# Сборка и хостинг runtime-пакетов через GitHub Actions

Эта папка описывает, как собирать и публиковать runtime-пакеты (imagefs, box64, wine, mesa, dxvk, vkd3d,
wine-mono, wine-gecko) **бесплатно на GitHub**. Сборка идёт в отдельном **публичном** репозитории
`kireikosasha/pmbos-runtime`. В нём лежит только копия pack-builder и workflow. Репозиторий приложения
остаётся приватным.

Готовые пакеты выкладываются как ассеты GitHub Release. Приложение по умолчанию берёт индекс отсюда:

```
https://github.com/kireikosasha/pmbos-runtime/releases/latest/download/index.json
```

Это постоянная ссылка: она всегда ведёт на `index.json` из самого свежего релиза, если он не помечен как
prerelease. Индекс содержит абсолютные ссылки на архивы своего тега, а также sha256 и размер каждого архива.
Приложение проверяет и то и другое.

| Файл | Что это |
|---|---|
| `workflows/build-packs.yml` | workflow. В репозитории пакетов он лежит по пути `.github/workflows/build-packs.yml` |
| `ci.sh` | вспомогательные команды для workflow: план, артефакты, кэш образов, проверка индекса, SOURCES, публикация, smoke-тест |
| `export.sh` | копирует всё нужное в клон репозитория пакетов |
| `fetch-release.sh` | скачивает паки релиза в `pmbos/packs-bundle/` для встраивания в APK (`pmbos/README.md`, «Встроенные паки») |
| `REPO_README.md` | README для репозитория пакетов |

## Первый запуск, шаг за шагом

1. **Создайте репозиторий** на github.com: справа вверху «+», затем «New repository».
   * Owner: `kireikosasha`, имя: `pmbos-runtime`.
   * Видимость: **Public**. Это обязательно: arm64-раннеры `ubuntu-24.04-arm` бесплатны только для
     публичных репозиториев, а ассеты релизов приватного репозитория приложение не скачает без токена.
   * Галочку «Add a README» можно поставить или не ставить. `export.sh` заменит README, только если тот
     сгенерирован им самим. Свой README он не тронет.
2. **Склонируйте** репозиторий рядом с проектом:
   ```bash
   git clone https://github.com/kireikosasha/pmbos-runtime.git ../pmbos-runtime
   ```
3. **Экспортируйте** pack-builder. Команду запускайте из корня этого (приватного) репозитория:
   ```bash
   bash pmbos/tools/pack-builder/github/export.sh ../pmbos-runtime
   ```
   В клоне появятся `.github/workflows/build-packs.yml`, `pack-builder/`, `loader/VERSION`, `README.md`,
   `.gitattributes` и `.gitignore`. Скрипт можно запускать повторно: каждый раз он заново копирует
   `pack-builder/` и workflow.
4. **Закоммитьте и запушьте:**
   ```bash
   cd ../pmbos-runtime
   git add -A
   git commit -m "pack builder"
   git push
   ```
5. **Проверьте настройки репозитория** (Settings):
   * Settings → Actions → General → Actions permissions: «Allow all actions» (или хотя бы actions от GitHub).
   * Settings → Actions → General → Workflow permissions: подойдёт любой вариант. Workflow сам запрашивает
     `contents: write` только для job'а публикации, но если организация запрещает запись для
     `GITHUB_TOKEN`, включите «Read and write permissions».
6. **Запустите сборку** одним из двух способов:
   * Actions → «Build packs» → «Run workflow». Все поля можно оставить пустыми. Получится релиз
     `packs-1.0.0-r<номер запуска>`.
     * `tag_suffix`: например `v1` даст тег `packs-v1`;
     * `dry_run`: собрать и проверить, но ничего не публиковать. Для первого раза это хороший вариант:
       пакеты останутся в артефакте `pb-dist` на 14 дней;
     * `prerelease`: опубликовать как prerelease. Приложение по умолчанию такие релизы **не** видит;
     * `wine_versions` / `box64_variants`: состав пакетов (по умолчанию берётся из `versions.env`);
     * `verify_wine`: `auto` только предупреждает, если `wine --version` под box64 не запустился;
       `1` в этом случае роняет сборку.
   * Или пушем тега: `git tag packs-v1 && git push origin packs-v1`.
7. **Подождите.** Первый запуск идёт **примерно 3–4 часа**, последующие примерно на 10–20 минут быстрее,
   потому что Docker-образы берутся из кэша. Job'ы и примерное время на стандартных раннерах (4 vCPU):

   | Job | Раннер | Время |
   |---|---|---|
   | plan | ubuntu-24.04 | < 1 мин |
   | fetch (скачивание и проверка исходников) | ubuntu-24.04 | 3–6 мин |
   | imagefs (pmbshm, libxcb, **glibc**, rootfs) | ubuntu-24.04-arm | 45–80 мин |
   | box64 (generic, sd8g2, sd888) | ubuntu-24.04-arm | 30–60 мин |
   | mesa | ubuntu-24.04-arm | 20–40 мин |
   | wine 11.0 и wine 11.22 (параллельно) | ubuntu-24.04 | 90–160 мин каждый |
   | repack (dxvk, vkd3d, mono, gecko) | ubuntu-24.04 | 3–5 мин |
   | package (xz -9e, затем verify) | ubuntu-24.04-arm | 25–50 мин |
   | publish (index, проверки, релиз, smoke) | ubuntu-24.04 | 5–15 мин |

   Самая длинная цепочка: fetch → wine → package → publish. Лимит одного job'а — 6 часов, у wine задан
   таймаут 340 минут.
8. **Проверьте релиз** на странице Releases. Там должны быть:
   * `index.json`, `SHA256SUMS`, `SOURCES.txt`, `pmbos-runtime-sources-<тег>.tar`;
   * архивы `imagefs-bookworm-1.0.0.tar.xz`, `box64-0.4.4.tar.xz`, `box64-sd8g2-0.4.4.tar.xz`,
     `box64-sd888-0.4.4.tar.xz`, `wine-11.0.tar.xz`, `wine-11.22.tar.xz`, `wine-mono-*.tar.xz`,
     `wine-gecko-2.47.4.tar.xz`, `mesa-26.3.1.tar.xz`, `dxvk-3.1.1.tar.xz`, `vkd3d-proton-3.1.tar.xz`.

   Job publish проверяет всё сам. Он сверяет sha256 и размер каждого архива с индексом, проверяет лимит в
   2 ГиБ на ассет и наличие типов rootfs/box64/wine/dxvk/vulkan-driver. После публикации он скачивает
   `index.json` по ссылке тега и по ссылке `releases/latest`, а также кусок архива через Range (как это
   делает приложение).
9. **Готово: plug&play.** Приложение само скачает индекс по ссылке по умолчанию и поставит недостающие
   пакеты при первом запуске Windows-программы. Ничего настраивать не нужно. Неудачная загрузка индекса
   (например, 404, пока релиза ещё нет) не кэшируется: при следующем запуске приложение попробует снова.

## Как обновлять пакеты

1. Внесите изменения в приватном репозитории: версии и хэши в `pmbos/tools/pack-builder/versions.env`,
   патчи, стадии (порядок описан в `pack-builder/README.md`, раздел «Updating versions»). Если меняется
   содержимое imagefs, поднимите `PACKSET_VERSION`.
2. Снова запустите `export.sh` в клон, затем `git commit` и `git push`.
3. Запустите workflow с новым `tag_suffix` или запушьте новый тег `packs-…`. Уже существующий тег
   workflow не перезаписывает и в этом случае падает на шаге plan.
4. Новый релиз сразу становится «latest». Приложение подхватит его, когда истечёт кэш индекса (1 час), или
   сразу после «Обновить» в приложении Runtime. Если удалить старый релиз, у кого-то в кэше может остаться
   индекс со ссылками на него. Приложение получит 404 на архив, само перечитает индекс и повторит установку.
5. Откат: откройте нужный старый релиз и нажмите Edit → «Set as the latest release».

Glibc жёстко привязан к загрузчику в APK (`loader/VERSION`). Если в приложении обновился
`pmbos/tools/loader`, пакеты **обязательно** нужно пересобрать: `export.sh` копирует новый
`loader/VERSION`, а `build-all.sh` не даст собрать несовпадающий glibc.

## Кэши, артефакты, лимиты

* **Кэши** (`actions/cache`, до 10 ГБ на репозиторий):
  * проверенные исходники `work/src`, ключ — хэш `versions.env` плюс состав wine/box64;
  * Docker-образы сборки по одному на тип (tools/arm64/amd64), ключ — хэш Dockerfile и `versions.env`.

  ccache не используется: пересборки редкие, а релизные сборки должны идти с чистого листа.

  Кэш GitHub привязан к ref: запуск по пушу тега `packs-…` видит только кэши своего тега и ветки по
  умолчанию, поэтому от кэша выигрывают запуски через «Run workflow» на ветке по умолчанию (`main`).
  Запуск по новому тегу собирает образы заново (это не ошибка, просто дольше на 10–20 минут).
* **Артефакты** между job'ами — `tar.zst` (сохраняют симлинки и права, чего `upload-artifact` сам не
  умеет). Самый большой из них — staged wine, примерно 0.3–0.6 ГБ. Это далеко от лимита в 10 ГБ на
  артефакт. Промежуточные артефакты хранятся 3 дня, `pb-dist` и `pb-release-meta` — 14 дней.
* **Ассеты релиза** — не больше 2 ГиБ на файл. Реальные архивы гораздо меньше: самые крупные
  (wine, imagefs, mono) весят от десятков до сотен МБ. Резать архивы на части не нужно, да приложение и
  не умеет их склеивать. Если когда-нибудь архив перерастёт лимит, publish упадёт с понятной ошибкой. Тогда
  уменьшите содержимое пакета или поменяйте `XZ_OPTS`.
* Если стадия rootfs (mmdebstrap) упадёт из-за прав внутри Docker, задайте переменную репозитория
  `PMB_DOCKER_ROOTFS_ARGS=--privileged` (Settings → Secrets and variables → Actions → Variables).
* При падении сборки логи wine, mesa и glibc прикладываются артефактом `logs-*`.

## Лицензии: что нужно соблюдать

Пакеты распространяют чужие бинарники:

| Компонент | Лицензия | Что требуется |
|---|---|---|
| glibc (пересобран с патчами) | LGPL-2.1+ | дать исходники **вместе с патчами** и скриптами сборки |
| Wine (пересобран с патчем) | LGPL-2.1+ | то же |
| VKD3D-Proton (бинарники upstream) | LGPL-2.1+ | указать, где взять исходники этой версии |
| box64 | MIT | сохранить копирайт и лицензию (`LICENSE.box64` в пакете) |
| Mesa | MIT и др. | сохранить лицензии (`share/LICENSE.mesa.rst` в пакете) |
| DXVK | zlib | не выдавать за своё, сохранить уведомление |
| wine-gecko | MPL-2.0 | указать, где взять исходники |
| wine-mono | MIT / LGPL / MPL | указать, где взять исходники |
| пакеты Debian в imagefs | разные (GPL/LGPL/MIT…) | файлы `copyright` сохранены в `usr/share/doc`, исходники доступны на snapshot.debian.org |

Workflow делает это автоматически. К каждому релизу прикладываются:
* `SOURCES.txt`: все компоненты с версиями, URL, sha256 и патчами, а также полный список пакетов Debian
  в imagefs с версиями исходных пакетов и ссылками на snapshot.debian.org;
* `pmbos-runtime-sources-<тег>.tar`: точные исходные архивы всего, что компилируется (glibc в виде
  dsc/orig/debian, libxcb, box64, wine, mesa), весь pack-builder (патчи, стадии, Dockerfile) и
  `loader/VERSION`.

Публичный репозиторий с тем же содержимым по нужному тегу — тоже «предложение исходников». Удалять старые
релизы можно, но для LGPL лучше держать исходники доступными, пока раздаются соответствующие бинарники.
Самим скриптам pack-builder стоит выбрать лицензию (например, MIT) и положить файл `LICENSE` в корень
репозитория пакетов. Патчи к glibc и wine являются производными работами и остаются под LGPL-2.1+.
